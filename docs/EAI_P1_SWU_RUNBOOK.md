## Current owner 2+2 isolation, backlog and immediate Sol Max rule (2026-11-17 KST)

- **P1 substantive attempt**: one materially different implementation/remediation approach actually exercised against code or directly observable failure, with `attempt_id, failure_cause, method_change, evidence_sha, outcome`. Read-only inspection, documentation edits, merely saying HOLD, CI polling, repeated identical failure, and mobile `ㄱ` do not increase the count. Existing attempt counts from before this policy are historical, **not** automatically all failures.
- **Initial window A (up to 2 actual failure attempts)**: first failed approach -> diagnose and make a meaningfully different attempt. If the same underlying blocker remains after two non-progress attempts, isolate the SWU into `ISOLATED_REDESIGN_PENDING`, record exact error and stopped method, and keep independent READY tasks moving. Never bypass owner scope or protective tests to force progress.
- **Redesign and window B (up to 2 additional actual attempts)**: cluster similar failures, select a changed algorithm/architecture/interface/environment and document why it addresses the cause; then allow at most two genuinely improved retries on the isolated SWU. Do not silently reset accumulated counts on a new chat/task ID. If blocked, record each new failure and retain isolation.
- **Noncritical exhaustion (2+2 failed)**: set `SOLMAX_BATCH_PENDING`, append to a shared batch by root cause with source SHA, requirements, failed approaches, required access/approval, safe reproduction commands and expected acceptance. Request Codex GPT-6.1 Sol Max to address the batch at the next appropriate handoff. Do not claim a Max review occurred without its output/evidence. If no READY remains, stop repetitive HOLD work and present consolidated backlog.
- **Essential/critical-path exception (immediately)**: if a task prevents necessary dependent SWUs, blocks P1 completion entirely, or would require unsafe assumptions/unauthorized actions, classify as `IMMEDIATE_OWNER_SOLMAX_REQUEST` **as soon as that is established**, even before initial two failures. Tell the user explicitly which EAI SWUs require **Codex GPT-6.1 Sol Max now**, why, what SHA/branch to inspect, what conditions must remain untouched, and which safe parallel tasks continue. The assistant cannot invoke a model it has not run; ask the user to initiate the handoff. No guessing acceptance.
- **No authority bypass**: a Sol Max request is a technical escalation, never automatic permission for original/customer file mutation, DB migration, external data send, paid services, LIVE Hydrogen, ACTIVE promotion, real Player actions, production or branch merge. These remain separately approved. Keep mandatory CI/branch protection and immediate auth/DB/secret checks. P2 whole validation remains locked until implementation candidate.
- **Queue state**: top-level `retry_escalation_policy`, `sol_max_escalation`; task-level `retry_stage`, `initial_nonprogress_attempts`, `post_isolation_nonprogress_attempts`, `retry_evidence`. Preserve historical `attempts_recorded` untouched where failure accounting is unknown. Do not infer failures from `PARTIAL_SOURCE` or High/HOLD status alone; documentation changes add 0 P1 progress.
